# ElX — этап 3: административный интерфейс Control

## Текущая граница компонентов

- `ElX-control` остаётся отдельным репозиторием. Его штатный сервис запускается с `serve-management`.
- `ElX-ui` предоставляет административный маршрут `/panel/elx`, а также API `/panel/api/elx/*`.
- `ElXray` продолжает исполнять политики и подтверждать освобождение слотов. UI не заменяет криптографический fence.

Панель и Control должны работать на одном доверенном хосте либо в одном пространстве Unix-socket. Нельзя публиковать Control management API в TCP или проксировать его через публичный URL подписок.

## Запуск

1. Подготовьте PostgreSQL Control и выполните миграции `elx-control migrate`.
2. Создайте каталог для Unix socket с разрешениями, ограничивающими запись (рекомендуется `0700`).
3. Установите переменную `ELX_MANAGEMENT_SOCKET` в абсолютный путь (например, `/run/elx/control.sock`) одинаково для процесса Control и панели.
4. Запустите `elx-control serve-management` с `ELX_CONTROL_POSTGRES_DSN`; проверьте, что сокет принадлежит правильному системному пользователю, разрешения `0600`.
5. Убедитесь, что пользователь процесса панели может подключаться к этому сокету. Если процессы работают от разных пользователей, предоставляйте доступ через выделенную доверенную группу и корректную политику ОС; не делайте сокет world-readable.
6. Откройте `/panel/elx` в администраторской сессии.

В интерфейсе предусмотрены просмотр подписок, устройств, сессий, занятости слотов, бюджета, выдач скорости по нодам, использования FUP, запрос `enqueue-drain` и явный `reconcile-fup`.

**Важно:** `enqueue-drain` переводит сессию в `draining`, но не освобождает слот. Для завершения требуется доставка в нужный ElXray и подписанный fence. `reconcile-fup` только ставит в журнал необходимые команды снижения; не повышает скорость автоматически. Обработчик отключений **уже существует**: штатный `elx-control serve-agent` на ноде вызывает `fencetransport.ApplyNext`, получает задание с Control по mTLS, выполняет `ElXray.DrainProfile` и отправляет подписанное подтверждение. Нода должна иметь настроенные ключи, доверенный профиль, socket ядра и постоянно работающий агент. Если подтверждение не пришло, слот остаётся занятым.

## Границы реализации

Пользовательский личный кабинет и проверки владения подпиской для отдельной учётной записи пока не реализованы. Запросы доступны только администратору панели либо токену `admin`. Токены мониторинга и межнодовой синхронизации не имеют прав на этот интерфейс. По одному лишь секретному URL подписки доступ не предоставляется. Добавлено создание дневных, недельных и месячных расписаний FUP через защищённый Control API с идемпотентным UUID и ограничением сниженной скорости купленным бюджетом. **Важно:** само создание расписания не подключает подписанные потоки учёта: до привязки нод/профилей/учётных stream assignments FUP нельзя считать реально контролирующим расход. Изменение купленного общего бюджета через UI пока не добавлено: это должно быть привязано к биллингу и отдельным проверкам прав, а не выполняться произвольным SQL-обновлением.

## Принятые ограничения

- На одну подписку — общий бюджет upload/download независимо по направлениям, в байтах/с на уровне Control и битах/с в UI.
- Административные команды проходят через Control journal и существующие механизм запрета старых политик.
- Отсутствие Control, PostgreSQL или проверки идентичности ядра должно давать отказ, а не обход ограничений.
- Миграции и таблицы Control не копируются в основную БД панели.

## Отзыв устройства

Администратор может отозвать устройство через `POST /panel/api/elx/entitlements/{id}/devices/{device}/revoke`.
В Control в одной транзакции под блокировками entitlement → device → owner устанавливается `revoked=true` и связанные доверенно привязанные сессии переводятся в `draining`. Агент ноды завершает соединения и получает подписанный fence. До подтверждения слоты остаются занятыми. Если у унаследованного владельца нет profile/core incarnation, он остаётся занятым и ответ явно указывает `undrainable` для ручного восстановления; нельзя считать его отключённым. Повторный отзыв идемпотентен.

## Создание FUP-расписания

Администратор задаёт cadence `day|week|month`, зону IANA, учитываемое направление `up|down|total`, порог в байтах и сниженную скорость в байтах/с по двум направлениям. Нули, превышение купленного бюджета и неизвестные часовые пояса запрещены. Даты считаются по календарным границам зоны с учётом перехода на летнее/зимнее время. `scheduleId` остаётся неизменным при повторе неопределённого ответа; повтор с тем же содержимым не создаёт новый период, с другой политикой — конфликт 409.

Для действующего FUP **необходимо** отдельно связать расписание с проверенными потоками подписанного учёта в Control. Не выдавайте клиенту обещание ограничения трафика, пока это условие не проверено.

## Личный кабинет пользователей

Добавлен отдельный путь `/lk` со своим Vite entrypoint, сессионной cookie `__Host-elx-lk`, независимой от администраторского cookie 3X-UI. Доступны регистрация по приглашению, вход по e-mail/паролю, получение списка своих подписок, запросы на отключение сессий и отзыв устройства, добавление ещё одной подписки по приглашению, создание до трёх дополнительных FUP-расписаний (с ограничением купленным тарифом).

Состояние и права хранятся в PostgreSQL Control (миграция 012). Приглашение одноразовое, его секрет никогда не записывается открытым текстом; пароль хранится как PBKDF2-HMAC-SHA256 с уникальной солью и 600000 итераций. Session-cookie хранит случайный секрет только в браузере, в БД есть лишь его SHA-256. Все изменяющие операции требуют серверную сессию, правильную связь `account → entitlement` и CSRF-подтверждение. Ссылка подписки, вход в панель администратора и произвольный UUID не предоставляют пользователю полномочий в ЛК.

Развёртывание требует **HTTPS**: cookie помечена Secure, HttpOnly, SameSite=Strict. Прямой TCP-доступ к Unix-сокету Control запрещён. Счётчик ошибочных входов хранится в PostgreSQL, но этого недостаточно для защиты от массового перебора случайных адресов: на Caddy/Nginx необходимо настроить глобальные и per-IP ограничения на `/lk/api/login`, `/lk/api/register` и `/lk/api/claim`. Требуется также защита от автоматизированной регистрации и наблюдение за аномальной активностью.

### Инвайты

После создания активной подписки в `elx_entitlements` оператор на доверенном сервере запускает:

```bash
ELX_CONTROL_POSTGRES_DSN='...' ./elx-control issue-invite -entitlement '<UUID подписки>' -ttl 72h
```

Секрет печатается **один раз**. Его следует передать покупателю по защищённому каналу и не сохранять в системном журнале. Пользователь заходит по `https://<домен>/lk`, выбирает регистрацию по приглашению и вводит e-mail, пароль и код. После входа он может добавить дополнительные подписки через новый инвайт. Доступ к ЛК не передаётся вместе со ссылкой подписки.

### Проверки и пока не закрытые вопросы

Добавлены тесты одноразовости приглашения, разграничения владельцев, защиты CSRF, самостоятельного выхода из сессии, ограничения попыток входа, строгой cookie и ограничения FUP-расписаний. Все проверки необходимо дождаться в актуальной CI-ветке до принятия PR.

Полная система платного доступа ещё требует интеграции биллинга/активации тарифа, подтверждения e-mail или восстановления доступа, жизненного цикла приглашений, доставки пользователям ошибок на устройство без входа, а также реальной привязки счётчиков трафика к каждому FUP-периоду. Эти функции нельзя заменять статусом «готово» по факту создания API и интерфейса.
